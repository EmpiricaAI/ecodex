# Slide deck: worktree-style MAS vs federated calibrated practices

Pre-empts the "why not git worktrees?" critique and positions the Empirica mesh
as a different layer entirely: a federation of sovereign, persistent, calibrated
practices coordinating governed action — not a parallel-checkout trick.

## How to use this

1. The figures are the SVGs in this folder (`01-…` → `05-…`), generated by
   `gen_mesh_visuals.py`. One figure per slide.
2. Drop **this file** + the five SVGs into NotebookLM (or any deck generator)
   as sources.
3. Paste the **customization prompt** below to steer the deck.
4. The **per-slide spec** is the ground truth for titles, figures, and talking
   points — keep the figure→slide mapping intact.

## Per-slide spec

### Slide 1 — Many agents, two architectures
- **Figure:** none (title slide) or `05-comparison.svg` as a teaser.
- **Talking points:** Running many AI agents in parallel is now table stakes.
  But "parallel agents" hides two completely different architectures. One
  parallelizes *work*; the other federates *agency*.
- **Speaker note:** Set up that the rest of the deck separates these two so the
  audience stops conflating them.

### Slide 2 — The objection: "why not git worktrees?"
- **Figure:** `01-worktree-mas.svg`
- **Talking points:** The common pattern — an orchestrator fans out N workers,
  each in an isolated git worktree (Claude Code's `Agent isolation:worktree` does
  exactly this). It's real and useful. But note the properties: one repo, one
  machine, one authority; workers are ephemeral clones that die at task end.
- **Speaker note:** Concede the strength up front — worktrees solve *execution
  isolation* (agent B doesn't stomp agent A's files). That honesty disarms the jab.

### Slide 3 — What a worktree can't do
- **Figure:** `01-worktree-mas.svg` (reuse) or `05-comparison.svg`
- **Talking points:** A worktree is by definition multiple windows onto **one**
  object store — the opposite of federation. It carries code diffs, not belief.
  It can't span repos, machines, or orgs. The git primitives that *do* span repos
  (submodules, subtree, monorepo) all collapse the federation into a single
  authority and history — exactly the sovereignty you're trying to keep.
- **Speaker note:** This is the pivot: worktrees are an intra-repo, single-authority,
  code-only tool. The thing we built lives on a different axis.

### Slide 4 — What we built: a federation of practices
- **Figure:** `02-federated-practices.svg`
- **Talking points:** N **sovereign practices** — each its own repo, its own
  calibration history, possibly a different machine, tenant, or org. They
  coordinate by message-passing: `collab` (open, ungated — knowledge can't act on
  you) and `propose` (ECO-gated — action can). Lead claim: a Claude Code practice
  and an ecodex/codex practice are first-class peers on the same mesh — that's
  demonstrable, not aspirational.
- **Speaker note:** Spanning machines/orgs is impressive but a skeptic shrugs
  ("so is SaaS"). Spanning *substrates* is the rare, hard-to-copy claim.

### Slide 5 — The unit: a seat, not a worker
- **Figure:** `04-practice-vs-worker.svg`
- **Talking points:** The deepest difference. A worker is ephemeral — spawn,
  work, die, respawn fresh, no identity, no memory. A practice is a persistent
  *seat* with a calibration trajectory running back to its birth. Identity lives
  in the seat; the model (the practitioner) is swappable and fungible. Swap
  Opus → a future model into the same seat and it inherits the trajectory.
- **Speaker note:** Analogy: an employee *role* that outlives whoever holds it,
  with a performance record attached. No agent framework or git primitive has this.

### Slide 6 — Governance scales with trust distance
- **Figure:** `03-trust-rings.svg`
- **Talking points:** This isn't an open agent-internet — it's a private,
  governed federation. Identity is canonical and server-resolved (you can't spoof
  a sender). Every actionable message is ECO-gated to a human/authorized decision.
  Claims are checked against calibration. And the gating *tightens with distance*:
  same-practice collab is open, cross-tenant is reviewed, cross-org is hard-gated
  (L3 ECO). The agentic-web failure modes — injection cascades, spoofing, runaway
  action — don't land here.
- **Speaker note:** Frame as defensibility, not limitation: graduated trust, not
  naive openness.

### Slide 7 — Side by side
- **Figure:** `05-comparison.svg`
- **Talking points:** Walk the table once: unit, authority, reach, lifetime,
  identity, what it carries, what it solves. Same number of agents on both sides —
  the contrast is *kind*, not *scale*.
- **Speaker note:** Let the table do the work; don't re-narrate every row.

### Slide 8 — The reframe
- **Figure:** none (closing statement).
- **Closing line:** *"It's not an agent internet. It's a federation of calibrated
  practices — persistent epistemic seats with track records — coordinating
  actionable intent across machines, users, substrates, and orgs, where the gating
  tightens with trust distance. The unit of federation isn't code, data, or
  compute. It's governed agency."*
- **Speaker note:** Land the one-liner: a pull request generalized beyond code,
  where calibration is the review signal. We use worktrees — for isolation. This
  is the layer above.

## Source narrative (grounding text for the generator)

Most "multi-agent" systems federate ephemeral workers: stateless, identical,
spun up per task, dead after. They use git worktrees for execution isolation —
giving each worker a clean checkout so it doesn't conflict with the others. That
is a real and good use of worktrees, and this system uses them for exactly that.

A worktree, though, is multiple working directories over a single git object
store, on a single machine, sharing one history. It is the opposite of
federation: one authority, many windows. It carries code diffs and nothing else —
no notion of an agent's confidence, no record of who approved a change, no shared
coordination state before any code exists. The git primitives that span repos
(submodules, subtree, monorepo) all work by collapsing independent repos into one
authority and one history, which destroys the sovereignty that federation needs.

The Empirica mesh is on a different axis. It federates *practices*: sovereign,
persistent epistemic seats, each with its own repository, its own accumulated
calibration trajectory, and an identity that lives in the seat rather than in any
model instance — the practitioner (the LLM) is swappable and fungible. Practices
can live on different machines, under different users, on different substrates
(Claude Code and ecodex/codex are peers on the same mesh), and across orgs. They
coordinate not by sharing a filesystem but by message-passing: `collab` is open
and ungated because knowledge cannot act on the receiver; `propose` is gated by
ECO (an authorized human/actor decision) because action can. Coordination state
that must outlive a thread lives in a Shared Epistemic Record (SER).

The result is a generalized pull request — over arbitrary shared state, not just
code — where calibration (the delta between an agent's stated belief and grounded
observation) is the review signal. It is not an open agent-internet: identity is
canonical and server-resolved, actions trace to ECO decisions, and governance
tightens as trust distance grows (same-practice → cross-tenant → cross-org). The
agentic-web failure modes — prompt-injection cascades, spoofed agents, runaway
action with no accountability — do not apply, because openness is replaced by
gated trust.
